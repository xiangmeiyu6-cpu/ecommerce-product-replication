# Managed release operation

Install the version manager from the repository README. Keep device-local settings outside the public package. Existing standalone copies need an explicit backup/adoption step. A copied SKILL.md alone is not a managed installation.

For each product task, create a batch evidence directory, then run this Skill's `scripts/managed-task.mjs begin --workspace <batch-directory> --receipt <batch-directory>/run-version.json`. Use the returned immutable `skill_path` and job ID. If re-reading that release's SKILL.md, reuse the active receipt rather than opening another task. Resume uses the same workspace and receipt. When returning the task outcome, run `finish --job <job_id>` even if capture remains partial; the batch files preserve the resume evidence, while the manager marker prevents accidental version changes only during an active turn/task. Explicitly resume the same evidence with a new task receipt if the previous receipt has been closed.

The manager checks the configured stable source at task entry. Compatible updates are staged and only activated while no task is active. Manual `check`, `update`, `rollback` and `doctor` use the installed launcher path. An interrupted task must be inspected and finished or abandoned before switching versions. Do not edit immutable installed release files. Repair the source release, test it and publish a new version.

## Evidence contract

Use `format: epr-evidence/v1`, `scope: capture|analysis|replication` and these structures:

- `evidence`: `{id, file, sha256, source, observed_at}`. Files use relative portable paths under the evidence directory. `observed_at` includes an explicit timezone. Retain source roles and observation context as additional fields when needed.
- `coverage`: entries for `identity`, `parameters`, `skus`, `main_images`, `details`, `video`, `reviews`, `qa`. Each has `status: complete|blocked|not_applicable`, `evidence_ids`, and `expected`/`observed` for complete entries. Details additionally require `end_verified: true`. Blocked and not-applicable entries need the actually observed `reason`, with evidence.
- `skus`: `{id,label,selected_verified,evidence_ids,price:{label,amount,currency,kind}}`; price kind is `before_discount|displayed|checkout|unknown`. Checkout prices require `checkout_verified: true`. An unavailable price must be handled as an access gap, not fabricated to satisfy the validator.
- `media`: `{role: main|detail,order,evidence_id,visually_reviewed}`. Main/detail sequences each start at1 and are contiguous; counts reconcile to their declared coverage. Preserve rendered images and reliable screenshots in actual page order.
- `review_sampling`: `{views:[{name,inspected,stop_reason,evidence_ids}],overlap:deduplicated|overlap_unknown,anonymous_templates_present,unique_buyers}`. Use `unique_buyers:null` when anonymous template events prevent buyer identification. Review samples are not exhaustive platform review totals.
- `findings`: `{id,module,kind,statement,evidence_ids}`. Kinds: `page_fact|user_fact|external_fact|inference|unknown|recommendation`. Inferences/recommendations include `mechanism`; unknowns include `limitation`. Recommendations add `action`, `placement` and `validation`. Preserve confidence and limits alongside conclusions.
- Analysis/replication modules: `positioning`, `audience_needs`, `scenarios_price`, `page_strategy`, `offers`, `feedback`, `competitiveness`, `advertising`, `reuse_judgment`. A genuinely unknown module has an unknown finding and a concrete limitation. Capture-only does not manufacture analysis findings. Replication additionally follows the existing strategy framework and user-product constraints; the structural validator alone does not certify those creative deliverables.
- `content_review`: `{status: passed|needs_review,reviewer,method,reviewed_finding_ids}`. Only record passed after actually checking evidence support, contradictions, regulated claims and recommendation usefulness. Do not fabricate reviewer identity or claim that schema checks replace substantive review.

Run `node <pinned-skill-path>/scripts/validate-evidence.mjs <batch-directory>/evidence.json`. Add `--require-complete` only when evaluating a complete-capture acceptance claim. Errors reject invalid evidence; a valid partial package keeps gaps and must not claim full completion. Missing semantic/visual review keeps content pending. Program checks only structure, references, hashes and declared attestations; verify actual rendered evidence through the browser and content-review workflow.

Keep remote delivery validation separate: use the fixed Feishu schema, compare all expected record keys and fields, verify every expected attachment, download representative categories, compare all saved-view settings and confirm the final batch status is visible. Record the actual Skill version, model information when available, quality/template versions, capture status and readback result in the batch evidence. Reuse existing fields, such as analysis version and snapshot notes; do not invent Feishu columns during a task.
